# 从 2.12 亿 Token 惨案到零成本 AI 编程助手：我的 Java 与 AI Agent 成长之路

> 这篇文章是仓库最早的首页内容，写于 2026 年 9 月。
> 后来仓库重新整理，它被收录为这篇文档 —— 代码会更新，但踩过的坑值得留着。

我是"大数据管理与应用"专业的大一新生。这是我在自学 Java 与 AI Agent 开发过程中，踩过坑、花过冤枉钱后，摸索出的一套（零成本、低延迟、电脑不卡顿的）云端 AI 辅助学习最佳实践。

## 一、缘起：一次"2.12 亿 Tokens"的惨痛教训

刚开始学习 Java 时，我使用 `Codex` 外接 DeepSeek API 来辅助学习。由于缺乏经验，我习惯性在同一个对话框里"无限套娃"，不断上传代码截图和历史记录。结果导致单次 API 请求携带了高达 27 万 Tokens，累计消耗 2.12 亿 Tokens！

虽说 DeepSeek 的定价较为便宜，但这也是一次不小的工程灾难：

- **Tokens 爆炸**：频繁使用截图和读取超长上下文让 API 计费瞬间失控。

那么这都会导致什么后果呢？

1. 模型"记忆中毒"：过长读取上下文导致 AI 变迟钝，回复变慢，甚至崩溃。
2. 电脑发热卡顿：本人试图在本地跑 6.7B 的模型 DeepSeek-Coder-6.7B（Ollama）时，我的 16GB 内存直接告急，严重影响开发体验。

## 二、破局：工程化思维与"外置记忆"

我开始反思，并用"软件工程"的思维去解决问题：

1. **"少量使用截图提问"**：改用「纯文本报错 + 20 行左右以及最小代码块」提问。
2. **"建立外置记忆"机制**：本地建立「Java 学习」文件夹，包括但不限于：学习路线、易错点整理、记忆清单。当我开启新对话时，只投喂 300 字左右的"提炼版进度"，而不是全文。
3. **实行"知识隔离"**：学完"数组"立刻关闭对话框，开启新对话去学"面向对象"，不会把不同模块混在一起。

## 三、架构选型：从本地 Ollama 到云端零成本 API

为了彻底摆脱 "Tokens 焦虑" 和 "电脑卡顿" 等问题，我对比了本地与云端方案：

### 1. 本地部署尝试（失败告终）

一开始，为了避免 API 费用，我尝试本地部署 `Ollama + DeepSeek-Coder-6.7B`。

- 优势：完全免费，不仅彻底断网可用，而且没有速率限制。
- 缺陷：6.7B 模型虽然小，但依然需要吃掉约 4G 左右的显存。加上 Windows 系统和 IDE 的开销，16GB 内存瞬间"捉襟见肘"。一旦跑起来，风扇狂转，电脑发热明显，甚至连浏览器都不敢多开。这种"为了省钱而牺牲开发体验"的做法，极度影响学习效率！

### 2. 云端 API 破局（最终选择）

放弃本地部署后，我通过 `CC switch` 配置 Codex 外接云端大模型。

- 探索过程：本人测试了 DeepSeek V4.1 flash（成本极低，但依旧有 Token 消耗），最终锁定智谱 AI 的 `GLM-4.7-Flash`。
- 爽点：它是目前国内承诺"永久免费"的云端大模型 API 接口，代码能力完全覆盖"找错、写骨架、给建议"的需求。最关键的是［计算全在云端］，我的电脑零压力、不发热、不卡顿。

**最终结论：**

作为大一学生，我的核心诉求是"快速解决问题"而非"部署大模型本身"。放弃 16GB 内存硬跑本地模型，转投云端 `GLM-4.7-Flash` 至少提高了学习效率不是吗？

## 四、核心配置：用 `CC switch` 给 Codex 外接各类大模型

在 `cc switch` 中新建配置：

- **配置名称**：`云-智谱-闪存`
- **供应商（提供者）**：`OpenAI 兼容`
- **Base URL**：`https://open.bigmodel.cn/api/paas/v4`
- **API Key**：从智谱开放平台获取（强烈建议存入系统环境变量，绝不可硬编码在代码里）
- **模型名称（型号）**：`glm-4.7-flash`

配置完成后，在 Eclipse 或终端使用 Codex 测试，响应极快，电脑毫无负担，且无任何 API 费用！

## 六、给初学者（以及未来的自己）的三条铁律

1. **API 密钥绝不上传 GitHub**：一律使用系统环境变量 `System.getenv()`，一旦泄露瞬间被盗刷。
2. **拒绝无脑截图**：截图是 Token 杀手。遇到报错，只复制控制台的红色纯文本。
3. **保持"开源"习惯**：每天用 Eclipse 来提交代码，保持 GitHub 常绿。
