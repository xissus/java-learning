# 怎么把自己的代码提交到 GitHub

> 这份文档写给刚学会敲代码、还没搞懂 Git 的人（也就是我自己）。
> 读完你只需要记住 **4 条命令**，每天写代码就是这么点事。

---

## 一、先搞懂三个词

刚接触 Git 时最晕的是分不清「提交」和「推送」。用一句话记住它们：

| 词 | 英文 | 比喻 |
| --- | --- | --- |
| 本地仓库 | local repository | 你桌子上的**练习本** |
| 提交 | commit | 给这次改动**拍一张快照**，并写一句说明贴在上面 |
| 推送到远端 | push | 把练习本**复印一份寄到 GitHub** 保管 |

关键点：**写代码 → 拍快照（commit）→ 寄出去（push）**，这是三个不同的动作。

- 只 `commit` 不 `push`：内容只在自己电脑上，GitHub 上还是旧的；
- 拍快照时 **不回写你的代码**，它只是记录「此刻文件长这样」，你原来的代码一个字都不会变；
- 拍完快照后你继续改代码，改出来的新内容会和快照产生差异，下次再拍一张就好。

为什么要这么麻烦？因为这样你**任何时候都能回到过去的某一张快照**。
比如以后某个程序写崩了，可以对比「上次能跑的那张快照」看看到底改了哪里，而不是凭记忆猜。

## 二、每天写代码，只要这 4 步

先打开终端（Windows 可以开 Git Bash），**cd 进项目目录**——也就是能看到 `src` 文件夹的那一层：

```bash
cd /d/Java学习/java-learning
```

然后按顺序敲下面 4 条命令。

### 第 1 步：先看看自己改了什么

```bash
git status
```

这条命令**只看不动**，非常安全，随时可以敲。你会看到两种情况之一：

- `nothing to commit, working tree clean` → 没有改动，什么都不用做；
- 一列**红色**的文件名 → 这些就是你改过的文件，红色表示"还没被拍进快照"。

> 养成习惯：**敲 `git add` 之前一定先 `git status` 看一眼**。
> 确认列表里没有你不该上传的文件（比如私人的笔记、密码文件）。

### 第 2 步：把改动放进"待提交"清单

```bash
git add .
```

那个 `.` 表示"当前目录下的所有改动"，注意末尾有个点，别漏掉。

敲完再 `git status` 一次，你会看到刚才**红色的文件名变成绿色**了。
绿色 = 已经放进了待提交清单，等着被拍照。

### 第 3 步：拍快照，写一句说明

```bash
git commit -m "feat: 完成 day03 的 if 分支练习"
```

引号里那句话叫**提交说明**，写给你未来的自己看。怎么写见下一节。

敲完会显示类似 `1 file changed, 2 insertions(+)`，意思是有 1 个文件变了、加了 2 行。

> ⚠️ 这一步**只在自己电脑上完成**，GitHub 上还看不到。

### 第 4 步：寄到 GitHub

```bash
git push
```

敲完等几秒，看到类似 `main -> main` 就成功了。
这时候刷新 GitHub 网页，你的改动就在上面了。

> 第一次在新电脑上用，要先把远端地址配好（只需做一次）：
> ```bash
> git remote add origin git@github.com:xissus/java-learning.git
> ```

## 三、提交说明怎么写

格式就一个：

```
类型: 做了什么
```

中间是**英文冒号加一个空格**。常用的类型只有 5 个：

| 类型 | 用在什么时候 | 例子 |
| --- | --- | --- |
| `feat` | 新增了一个功能、完成了一课练习 | `feat: 完成 day03 的猜数字练习` |
| `fix` | 修好了一个 bug | `fix: 修正 Table99 少打印一行的问题` |
| `docs` | 只改了注释或文档 | `docs: 补充 Scanner 的中文注释` |
| `style` | 只调整格式，逻辑没变 | `style: 把 Tab 缩进改成 4 个空格` |
| `refactor` | 代码结构调整，功能不变 | `refactor: 把求最大值抽成方法` |

**写说明的一条原则：写"做了什么"，不要写"改了哪个文件"。**

- 不好：`修改 ArrayTest1.java`
- 好：`feat: ArrayTest1 增加求平均分的功能`

原因很简单：三个月后你翻提交记录，看到"修改 ArrayTest1"完全想不起来干了啥，
而"增加求平均分的功能"一眼就明白。

## 四、动手之前，先确认邮箱是对的

这是**最容易踩、后果最隐蔽**的一个坑：

> GitHub 判断"这次提交算不算你的贡献"，**只看提交里记录的邮箱，跟不跟你的账号绑定**。
> 名字写什么都不影响。

如果邮箱不对，提交会成功、代码也在仓库里，但**你的主页贡献图上永远不会出现那一天的绿格子**。

先检查一下：

```bash
git config --global --get user.email
```

**正确的结果应该是：**

```
2032168967@qq.com
```

如果不是，用这两条命令改成正确的（只做一次，以后一直有效）：

```bash
git config --global user.name "杨训杰"
git config --global user.email "2032168967@qq.com"
```

> **血泪教训**：我早期有 4 次提交就是白做的——其中 2 次用的邮箱是
> `20321@100.68.2.7`（Git 没配置时按电脑名自动生成的假邮箱），
> 另外 2 次用的是 `你的GitHub注册邮箱@example.com`——那是从教程里复制命令时
> **忘了替换的占位符**。
> 所以：**从任何地方复制 git 命令，看到 `你的...@example.com` 这种写法，先改成自己的邮箱再回车。**

## 五、不想用命令行？在 Eclipse 里也能提交

Eclipse 自带 Git 功能，习惯用鼠标的话可以这样：

1. **首次关联**：右键项目 → `Team` → `Share Project...` → 选 `Git` → 勾选项目 → `Finish`；
2. 改完代码后：右键项目 → `Team` → `Commit...`；
3. 在弹出的窗口里填 `Commit message`（就是提交说明），勾选要提交的文件；
4. 点 **`Commit and Push`** —— 一步完成本地快照 + 推送到 GitHub；
   如果只想先存本地，就点 `Commit`，之后再单独 `Push`。

> 如果右键菜单里**找不到 `Team`**，说明这个项目还没和 Git 关联，先做上面第 1 步。

**命令行和 Eclipse 是同一件事的两种操作方式**，用哪种都行，结果完全一样。
命令行多敲几次之后你会发现它更快，而且报错信息更清楚。

## 六、常见报错怎么办

| 屏幕上出现什么 | 什么意思 | 怎么办 |
| --- | --- | --- |
| `fatal: not a git repository` | 你不在项目目录里 | 先 `cd /d/Java学习/java-learning` |
| `Please tell me who you are` | 没配置名字和邮箱 | 做第四节那两条 `git config` 命令 |
| `nothing to commit, working tree clean` | 没有改动，或者已经提交过了 | 正常现象，不用管 |
| `Updates were rejected ... non-fast-forward` | GitHub 上有你本地没有的内容 | 先 `git pull`，再 `git push` |
| `Permission denied (publickey)` | SSH 密钥没配好 | 已经配过了；若换电脑需重新配 SSH |
| `fatal: destination path ... already exists` | 对着已经存在的文件夹又 clone 了一次 | 删掉多出来的文件夹，别重复 clone |
| Eclipse 里文件名前是**黄色问号** | 新文件还没被加入 Git | 右键 → `Team` → `Add to Index` |

## 七、贴墙速查卡

```bash
cd /d/Java学习/java-learning   # 1. 进项目目录
git status                     # 2. 看看改了哪些文件
git add .                      # 3. 全部放进待提交清单
git commit -m "feat: 说明"     # 4. 拍快照并写说明
git push                       # 5. 寄到 GitHub
```

**只多记一条**：不小心敲错了、想撤销刚才的 `git add`，用 `git restore --staged .`
（它只把文件从待提交清单里移出来，**不会删你的代码**）。

---

## 八、三条铁律

1. **一次提交只干一件事。** 别把「新写的练习 + 顺手改的注释 + 格式化」攒成一次，
   分成 3 次提交，以后回溯才找得清楚。
2. **先 `git status` 再 `git add`。** 那条命令只看不动，是最便宜的保险。
3. **说明写给自己看。** 你不是写给机器看的，是写给三个月后翻记录、一脸茫然的自己。

---

> 如果你用不确定的参数或顺序，也可以直接跟助手的对话里说一句「帮我提交这次的改动」，
> 它会跑 `git status` 确认改动、帮你写一句合适的提交说明、再推送上去。
> 但**建议你至少自己手动跑熟上面这 5 条命令**——
> 这是每天都在用的基本功，比记住任何一个 Java 语法点都更值钱。
